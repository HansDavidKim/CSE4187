# Retention 모델 구현 계획

작성일: 2026-11-04

구현 중 추가 합의: ML 비교군은 LightGBM·CatBoost·XGBoost 3종, DL 비교군은 LSTM·GRU 2종으로 확장한다. 아래의 최초 2종 트리·LSTM 단일안보다 이 추가 합의를 우선한다. 데이터는 확정된 7종 입력이 모두 제공된다고 가정하며, 동일 스키마의 계약 fixture로 end-to-end smoke test한다. Cosmetics를 임의로 주문·쿠폰 데이터로 바꾸지 않는다. 현재 실행 방법과 확인한 결과는 `readme.md`와 실행별 `comparison.md`를 참고한다.

## 1. 목표와 범위

프로젝트 루트의 `RETENTION_REQUIRED_FEATURES.md`에 확정된 7종 입력이 제공된다고 가정하고, 고객별 미래 이탈 확률을 예측하는 학습·추론 파이프라인을 구현한다. 이 문서는 구현 계획이며, 모델 구현이나 성능 검증을 완료했다는 뜻은 아니다.

모든 소스·설정·의존성 목록·테스트·생성 산출물은 `retention/` 안에 둔다. 루트의 `config/`, `features/`, `common/`, `uplift/`, 시뮬레이터 코드는 수정하지 않는다. 외부 데이터는 읽기만 한다. 기존 빈 `retention/readme.md`는 향후 실행 안내에 사용한다.

과제 요구인 트리 모델 2종 이상, 불균형 처리, 5-fold 검증·튜닝·SHAP, LSTM 또는 Transformer, ML/DL 동일 테스트 비교·앙상블 실험을 단계적으로 충족한다. 피처 30개 이상·변화 피처 5개 이상·세션 품질 3개 이상·시퀀스 피처 2개 이상도 내부에서 산출하되, 후보를 전부 최종 모델에 강제로 넣지는 않는다. 과제의 공용 `docs/`·`results/` 산출물 경로는 이번 작업 범위에서 수정하지 않고 대응 자료를 `retention/`에 생성한다.

## 2. 입력 계약과 검증

전체 기간의 기록을 한 번 읽고 내부에서 고객·시점별 표본을 만든다. 아래 이름은 논리 테이블이며, 물리 파일은 CSV 또는 Parquet을 사용한다. 물리 파일명·경로는 로컬 설정에서 지정하고 대규모 이벤트를 중복 전송하지 않는다.

| 논리 테이블 | 입력 필드 | 검증 기준 |
| --- | --- | --- |
| 고객 | `customer_id`, `signed_up_at` | 고객 키 유일성, 가입 시각 파싱. 최초 행동을 가입으로 대체하지 않음 |
| 세션 | `session_id`, `customer_id`, `started_at`, `ended_at` | 고객 존재, 종료가 시작보다 빠르지 않음. 연결 키는 고객+세션. 결측 세션 ID는 임의의 한 세션으로 묶지 않음 |
| 이벤트 | `event_id`, `customer_id`, `session_id`, `event_at`, `event_type` | 이벤트 키·지원 행동·고객/세션 연결 검사. 조회·추가·제거·구매 별칭은 명시적 매핑 |
| 주문 | `order_id`, `customer_id`, `session_id`, `purchased_at` | 주문 키 유일성, 고객·세션 연결. 주문과 구매 이벤트를 이중 계산하지 않음 |
| 주문 상품 | `order_id`, `product_id`, `unit_price`, `quantity` | 주문 존재, 구매 당시 단가·수량의 유효성. 상품 행의 중복 여부를 근거 없이 추정하지 않음 |
| 쿠폰 발송 | `coupon_id`, `customer_id`, `policy`, 선택적인 `sent_at`, `expires_at` | 쿠폰 키·고객 연결, 제공 시 발송/만료 순서 검사. 정책 식별과 정의를 보존 |
| 쿠폰 사용 | `coupon_id`, `order_id` | 쿠폰·주문 존재와 고객 일치. 사용 시각은 주문 구매 시각. 다중 적용은 정책 규약과 대조 |

ID는 문자열로 취급하고 모델의 수치 입력에서 제외한다. 시각은 공통 시간대로 정규화한다. 쿠폰 사용은 주문의 구매 시각에 연결하고, 주문 총금액은 `Σ(unit_price × quantity)`로 산출한다. 반복 이벤트 수를 수량으로 사용하지 않는다.

필수 키 중복·잘못된 참조·시각 오류·지원하지 않는 값은 검증 보고서에 기록한다. 모호한 값을 조용히 삭제하거나 0으로 대체하지 않고, 기본은 해당 실행 중단 및 오류 위치 안내로 한다. 세션 ID·선택 시각처럼 허용한 결측은 그 규칙대로 처리한다. 음수 가격은 환불로 추정하지 않고 데이터 계약 위반 여부를 보고한다.

`policy`가 opaque string이면 문자열을 임의로 해석해 할인율을 만들지 않는다. 초기 Monetary는 할인 전 주문금액을 사용한다. 정형 정책 정의가 제공되고 필요성이 확인될 때 할인 후 금액을 추가한다. 물건별 쿠폰 적용은 연결 규약이 없으면 추정하지 않는다.

## 3. 처음 구현할 예측 문제

아래는 확정 요구가 아닌 **실행 가능한 초기 기본값**이다. 로컬 설정으로 바꿀 수 있도록 하고 결과마다 정의를 저장한다.

| 항목 | 초기 구현안 |
| --- | --- |
| 타깃 | 기준시각 이후 30일 동안 새 세션 시작이 없으면 이탈 1, 있으면 유지 0 |
| 기준시각 | 전체 기간 중 매주 한 번 생성. 시각 경계는 UTC로 통일 |
| 입력 창 | 직전 30일. 변화 비교는 최근 14일과 그 이전 14일 |
| 최근성·가입/구매 여정 | 기준시각 이전의 제공된 전체 이력에서 계산 |
| 초기 대상 | 가입 후 30일 이상이고 직전 30일에 방문한 고객. 신규·이미 휴면 고객은 별도 상태로 보고하며 초기 모델 대상에서 제외 |
| 결과 정책 | 학습 데이터가 생성된 발송 정책 아래의 이탈 위험. 추가 미발송 조건의 인과적 위험으로 표시하지 않음 |

입력은 `[t−W, t)`, 정답은 `[t, t+H)`로 구분한다. `t`에 발생한 새 행동은 정답 쪽에 포함한다. 진행 중 세션은 당시까지 알려진 이벤트만 사용하고 미래 종료 시각으로 최종 세션 길이를 만들지 않는다.

라벨 확정에는 전체 생성 종료/수집 종료를 확인할 수 있는 실행 설정이 필요하다. 이는 모델 실행 설정이며 새로운 고객별 필드 요청이 아니다. 종료 경계가 확인된 경우 `t+H`까지 결과를 확인할 수 있는 표본만 학습·평가한다. 외부 데이터에서 실제 수집 종료·누락 여부가 불명확하면 명시적 가정을 설정해야 하며, 이벤트 최댓값을 실제 수집 종료로 자동 간주하지 않는다. 확인되지 않은 무행동을 확정된 이탈로 보고하지 않는다.

초기 대상 조건과 시작 시각도 같은 관측 가정을 전제로 한다. 조건으로 제외한 고객에게 임의의 점수를 채우지 않고 제외 사유를 남긴다. 추론 시 미래 기록은 필요하지 않다. 미구매 타깃·다른 기간·신규 모델은 기본 흐름 검증 후 별도 실험으로 추가한다.

## 4. 내부 피처 구성

시뮬레이터에 집계·변화율을 추가 요청하지 않는다. 주문을 먼저 주문 단위로 집계한 뒤 세션·이벤트·쿠폰을 연결해, 다대다 조인으로 주문 수·금액이 부풀지 않도록 한다.

| 피처군 | 초기 후보 |
| --- | --- |
| 최근성·기본 이력 | 마지막 방문 경과일, 마지막 구매 경과일, 가입 후 경과일, 구매 경험 지시자, 구매 간격 계산 가능 지시자 |
| 최근 30일 활동 | 세션 수, 활동일 수, 조회 수, 장바구니 추가 수, 제거 수, 구매 이벤트 수, 주문 수, 할인 전 구매금액 합계, 평균 주문금액, 고유 구매 상품 수 |
| 세션 품질 | 완료 세션 평균 길이, 완료 세션당 조회 수, 구매 완료 세션 비율, 장바구니가 있는 완료 세션 중 구매 세션 비율 |
| 구매 주기 | 과거 평균 구매 간격, 마지막 구매 경과일/평균 구매 간격 |
| 변화 | 세션 수·조회 수·장바구니 추가 수·주문 수·구매금액의 최근 14일/이전 14일 변화율 5종과 각각의 비교 원값 |
| 시간대 | 주말 활동 비율, 야간 활동 비율. 구간과 시간대는 설정에 고정 |
| 여정 | 가입/구매 이력 기반 단계, 현재 단계 체류일. 단계 정의를 피처 사전에 명시하며 미래 이탈 라벨로 단계를 만들지 않음 |
| 순서 요약 | 연속 행동 전환 수, 최근 행동 연속 반복 길이. 동일 시각의 순서를 요구하지 않는 과거 시각 그룹 기준으로 계산 |
| 쿠폰 | 과거 사용 수. `sent_at`이 제공될 때만 과거 발송 수·최근 발송 경과일을 추가하고, 만료 시각과 사용 기록이 충분할 때 유효 미사용 쿠폰 수 추가 |

이 목록에서 30개 이상을 정의·산출하고 피처별 산식·필요 기록·시간 범위·결측 처리를 사전으로 저장한다. 과제의 시퀀스 피처군은 우선 명시적인 순서 요약 2종으로 구성하며, 과제에서 학습 임베딩/군집까지 요구한다고 해석되는지 확인한 뒤 필요한 경우에만 확장한다.

결측·불안정 값의 규칙은 다음과 같다.

- 관측됐고 행동이 없으면 횟수·금액은 0. 구매 없음의 최근성·평균 주문금액은 null과 관련 지시자로 구분한다.
- 구매 1회로 간격을 계산할 수 없으면 null로 남긴다. 동시 주문으로 평균 간격이 0이면 주기 비율도 유효하지 않은 값으로 처리한다.
- 변화율은 이전 값이 양수일 때 계산하고, 0이면 null 및 이전 0 지시자를 제공한다. 임의 epsilon으로 큰 비율을 만들지 않는다.
- 클리핑·대체·범주 인코딩·스케일링은 학습 구간 안에서 적합한다. 검증/테스트의 분포를 사용하지 않는다.
- 쿠폰 발송 시각이 없으면 발송 레코드를 과거 어느 시점에 알았는지 알 수 없으므로 전체 발송 수·정책 목록을 과거 피처로 소급하지 않는다. 쿠폰 사용은 과거 주문에서 확인된 건만 사용한다.

## 5. 모델과 선택 순서

1. **기준선:** 학습 이탈률 상수 예측, 방문 최근성 기반 로지스틱 회귀. 복잡한 모델의 추가 가치를 비교할 기준을 만든다.
2. **ML:** LightGBM과 CatBoost 이진 분류기를 비교한다. 최초 불균형 처리는 학습 표본에서 산출한 클래스 가중치로 하고, 확률 보정 영향을 별도 평가한다. 데이터 복제나 SMOTE부터 도입하지 않는다.
3. **DL:** PyTorch의 단방향 LSTM 하나로 시작한다. 이벤트 종류 임베딩, 이전 시각 그룹과의 간격, 세션 정보, 마지막 활동 경과시간을 입력으로 사용한다. 시간 그룹 안에서는 이벤트별 개수/존재로 표현해 미확인 행 순서를 학습하지 않는다. 세션 ID가 없으면 임의 경계를 만들지 않고 결측 상태를 표시한다.
4. **DL 길이·학습:** 최근 128개 시각 그룹을 시작 후보로 두고 절단율과 성능을 확인한다. 패딩·mask·빈 이력 처리를 구현하고 검증 손실로 Early Stopping한다. 시간/수치 정규화와 어휘는 학습 자료에만 적합한다.
5. **선택:** 개발 자료 안에서 작은 Optuna 탐색으로 튜닝한다. 최종 테스트를 보고 재튜닝하지 않는다. ML과 DL은 동일 고객·기준시각·정답·분할에서 비교한다.
6. **앙상블:** ML/DL 확률의 고정 평균부터 실험한다. 검증에서 개선이 없으면 단일 모델을 선택한다. 확률 보정은 검증된 필요성이 있을 때 독립된 시간 검증 자료 또는 학습 외 예측으로만 적합한다.

ML/DL 비교는 입력 표현도 다른 시스템 비교라는 점을 보고한다. 순서 자체의 효과를 주장하려면 같은 정보량에서 순서를 제거한 DL 표현과 추가 비교한다. Transformer·복수 DL·학습 군집·여러 보정기를 한꺼번에 구현하지 않는다.

## 6. 평가와 누출 방지

주 평가는 기존 고객의 미래 예측을 확인하는 시간 평가로 한다. 최종 테스트는 가장 뒤의 성숙한 기준시각 구간으로 미리 고정한다. 개발 기간에는 **5개 rolling-origin fold**를 구성해 과거로 학습하고 다음 구간을 검증한다.

각 fold의 학습 표본은 정답 구간이 검증 시작 전에 완전히 끝나야 한다. Early Stopping용 표본은 fold 학습 기간의 뒤쪽에서 따로 분리하고, 여기도 결과 창 경계 규칙을 적용한다. 최종 검증 fold를 Early Stopping과 평가에 동시에 사용하지 않는다. 학습은 미래 고객 이력을 읽을 수 없고, 검증 시점까지 실제로 발생한 과거 이력은 사용할 수 있다.

5개 fold를 만들기에 기간·클래스 표본이 부족하면 몰래 랜덤 분할로 대체하지 않는다. 부족한 기간/표본과 가능한 fold 수를 보고하고 설정 조정을 요구한다. 고객을 완전히 분리하는 일반화 평가는 별도의 보조 실험이며 시간 평가와 결과를 섞지 않는다.

같은 고객의 주별 정답 구간은 겹칠 수 있다. 불확실성은 고객 단위 bootstrap 등으로 평가하고 행을 독립 고객처럼 세지 않는다. 단일 클래스 평가 구간은 AUC를 계산할 수 없음을 명시한다.

평가 지표는 ROC-AUC, PR-AUC와 양성 비율, Log Loss, Brier Score, 확률 보정 곡선이다. 임계값별 Precision/Recall도 개발 검증에서 분석하고 목적을 명시해 임계값을 선택한다. 과제의 AUC 0.78은 달성 여부를 보고할 기준이며 사전 보장하지 않는다. 테스트를 보고 데이터 생성 규칙을 바꾸지 않는다.

SHAP은 선택된 트리 모델에 대해 대표 표본으로 전역 상위 10개와 고객별 설명을 생성한다. 예측 점수 기여를 설명하며 인과적인 이탈 원인이나 쿠폰 효과로 해석하지 않는다.

## 7. 외부 연동 범위

추론 결과는 고객·기준시각, `churn_probability`, 타깃 정의·기간, 결과 정책 설명, 모델 버전을 포함한다. 제외/실패 표본은 점수 대신 상태와 사유를 반환한다. 원본 ID를 그대로 보존하고 여러 모델의 결과를 같은 키로 연결할 수 있도록 한다.

초기 API는 `fit` / `predict_proba`와 테이블 단위 배치 예측으로 충분하다. CLI는 `python -m retention ...` 형태로 실행하고 결과 디렉터리를 명시적으로 지정한다. 예측 시 학습에 사용한 피처 생성 설정·전처리·모델을 함께 로드한다.

Uplift 담당자에게는 결과 모형으로 쓸 수 있는 학습/예측 코드를 제공할 수 있게 구성하되, T/X/H를 Retention 안에 구현하지 않는다. 현재 스키마만으로 무작위 배정·미래 추가 발송 규칙을 알 수 없으므로 `predict(treatment=0/1)`을 단순히 추가해 인과 예측이라고 표시하지 않는다. 처치별 학습 표본과 정책 조건이 합의된 뒤 어댑터를 연결한다. H의 정의는 미정으로 남긴다.

Downstream 학습에서 OOF 예측을 실제 요구할 때만 추가한다. 이때 보류 표본은 피처 변환뿐 아니라 튜닝·보정·모델 선택에서도 제외해야 한다. 일반 검증 예측을 엄격한 OOF라고 이름 붙이지 않는다. CLV를 수정하거나 Retention 점수를 CLV 필수 입력으로 강제하지 않는다.

## 8. 파일 구성과 실행 산출물

구현 시 다음 정도로 시작하며 서비스·registry·추상 팩토리를 먼저 만들지 않는다.

```text
retention/
  IMPLEMENTATION_PLAN.md
  readme.md
  __init__.py
  __main__.py             # 데이터 점검 / 학습 / 평가 / 추론 CLI
  config.yaml            # 입력 경로, 기간, 대상, 시간 분할, 모델 설정
  requirements.txt       # Retention 실행에 필요한 의존성
  data.py                # 로딩, 키/시각 검증, 데이터 품질 보고
  dataset.py             # 고객·시점 표본, 정답, 분할
  features.py            # 집계·시퀀스 변환 및 피처 사전
  models.py              # 기준선·트리 모델과 저장/로드
  sequence.py            # LSTM 데이터셋·모델·학습
  pipeline.py            # 학습·추론 절차와 설정 재현
  evaluate.py            # 지표·보정·SHAP·비교 리포트
  tests/                 # 시간 경계·키 연결・추론 일관성 등
  artifacts/             # 실행별 설정·캐시·모델·결과
```

의존성은 DuckDB, pandas/NumPy, scikit-learn, LightGBM, CatBoost, PyTorch, Optuna, SHAP, matplotlib, pytest를 기능별로 사용한다. 실제 환경과 호환되는 버전을 설치·검증한 후 고정하며, 외부 시뮬레이터의 의존성 파일은 수정하지 않는다.

약 2천만 행 규모를 고려해 DuckDB로 필요한 컬럼만 읽고 기간·고객별 집계를 수행한다. 모델 입력 크기의 집계표만 pandas로 가져오며, 이벤트를 고객별 전체 기간으로 여러 번 복사하지 않는다. 캐시는 로컬 Parquet을 사용한다. GPU 필수로 가정하지 않고 DL은 작은 설정으로 CPU에서도 점검할 수 있게 한다.

실행별로 입력 파일 식별 정보, seed, 설정, 데이터 검증 보고, 표본/라벨/분할 목록, 피처 사전·목록, 모델·전처리, 성능 비교와 예측 파일을 저장한다. 데이터 릴리스의 불변성을 확인할 수 있는 식별 정보와 동일 설정으로 재실행 가능한 구성을 우선한다.

## 9. 구현 단계와 완료 조건

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 1 | 입력 로더·검증·작은 합성 fixture | 7종 입력의 키 연결과 시각 규약 검사. 원본 파일 무수정 |
| 2 | 표본·라벨·분할·첫 피처 | 미래 행을 추가/변경해도 과거 피처 불변. 끝나지 않은 라벨 제외. 주문 상품 조인으로 건수·금액이 부풀지 않음 |
| 3 | 최근성 기준선·단일 트리 end-to-end | 설정 한 개로 학습→저장→재로드→미래 없이 추론 가능 |
| 4 | 피처 요구 충족·트리 2종·5-fold·튜닝 | 30개 이상 피처 사전, 요구 피처군, 누출 없는 동일 평가 결과. 클래스 가중치와 보정 상태 보고 |
| 5 | LSTM·앙상블·SHAP·최종 평가 | ML/DL 같은 테스트, 검증 기반 모델 선택, 확정한 모델들의 테스트 결과와 한계 보고 |
| 6 | 배치 추론·담당자 연동 안내 | 제공 가능한 입력과 필요한 입력을 검증하고 동일 키로 결과 반환. Uplift 추가 계약은 별도 명시 |

테스트는 시간 경계, 진행 중 세션, 쿠폰 시각 누락, 쿠폰 사용/주문 연결, 주문 상품 합산, 신규/무구매/null, 동일 시각 순서 불변, 분할의 라벨 성숙, 모델 저장/로드 일관성을 검증한다. 소형 fixture는 계약 검증용이며 실제 정확도를 입증하는 데이터가 아니다.

전체 흐름을 먼저 작은 데이터로 검증한 다음 전체 기간 데이터로 확대한다. 실제 입력이 아직 확정 스키마로 제공되지 않았다면 현재 Cosmetics CSV를 임의의 주문·쿠폰 데이터로 변환해 구현 완료로 보고하지 않는다.

## 10. 학습 실행 전에 확정할 설정

코드 뼈대·입력 검증은 위 계약으로 시작할 수 있다. 실제 학습·평가 결과를 해석하기 전에는 다음 설정을 확정하고 실행 기록에 남긴다.

1. 이탈을 미방문으로 볼지 미구매로 볼지, 예측 기간과 대상 고객 조건.
2. 전체 기록의 생성/수집 종료와 누락에 대해 실제로 확인할 수 있는 범위 및 필요한 가정.
3. `policy`의 표현, 다중 쿠폰·물건별 적용 지원 여부, 발송 시각을 제공할지 여부.
4. 평가 기간과 5개 시간 fold를 구성할 충분한 기록·클래스 표본의 존재.
5. Retention이 관측 정책의 이탈 예측만 제공할지, 이후 Uplift의 처치별 결과 학습까지 지원할지.
