# Retention 결정 사항과 구현 계획

갱신일 2026-11-18

현재 구현에는 정책별 학습, 검증 모델 보존, 확률 보정 선택, 피처 제거 실험, 독립 평가·모니터링, 원자적 모델 공개와 공개 API가 반영됐다. 상세 실행 결과는 [검증·비교 보고서](MODEL_COMPARISON.md)와 실행별 리포트에 기록한다.

현재 팀 합의, 각 파트의 README, 실제 구현을 기준으로 Retention의 보완 범위와 검증 절차를 정리한다. 확정된 계약은 아래 기준을 적용하고, 모델·피처·보정 방식의 최종 선택은 개발 검증 결과로 정한다.

## 1. 적용 기준과 작업 범위

- 기간과 실험 조건은 이번 대화에서 확인한 팀 합의와 각 파트의 최신 README를 따른다. 기능·성능·필수 산출물은 요구사항 PDF와 저장소의 요구사항 문서를 함께 확인한다.
- 구현 대상은 `retention/` 안의 소스·설정·테스트·문서·실행 산출물이다. 시뮬레이터, Uplift, CLV의 공개 API와 설정을 읽어 연결한다.
- 외부 변경이 필요한 버그나 연동 장애를 발견하면 원인, 영향, 필요한 변경을 사용자에게 먼저 설명한다.
- 개발·검증에는 프로젝트 루트의 `.venv/Scripts/python.exe`를 사용하고 실행별 Python 경로와 패키지 버전을 기록한다.
- 기존 7종 CSV/Parquet fixture와 시간순 분할 경로는 호환성 검증에 활용한다. 현재 기본 실행은 시뮬레이터 공식 입력과 단일 실험 기준시점의 고객 분할을 사용한다.

## 2. 확정된 결정 사항

| 항목 | 적용 기준 | 근거 |
| --- | --- | --- |
| 이탈 정의 | 기준일 이후 28일 동안 새 세션 시작이 없으면 `y=1`, 있으면 `y=0` | 팀 합의·공식 로더 |
| 예측 대상 | 기준일 직전 28일에 방문했고 기준일 전에 가입한 고객. 짧은 가입 이력도 이 조건을 충족하면 포함 | 현재 시뮬레이터 계약 |
| 라벨 기간 | `[t0, t0 + 28일)` 전체가 관측된 표본을 학습·평가에 사용 | 공식 로더·원장 대조 |
| 입력 경계 | `t0` 이전에 확인 가능한 기록을 사용. `t0`에 발생한 새 행동은 결과 구간에 포함 | 시간 누출 방지 |
| 피처 창 | KIT39의 30일 집계, 이전 30일과의 차이, 90일 간격 등 등록된 정의를 사용 | 시뮬레이터 README |
| 쿠폰 실험 | 고객별 1:1 고정 배정. 발송군에 기준일 10% 쿠폰 1회, 28일 유효. 대조군은 미발송, 결과 구간 중 추가 발송 없음 | 시뮬레이터·Uplift 계약 |
| 기본 정책 조건 | `observed_experiment_mix`로 발송·미발송군을 함께 학습한 관측 정책의 위험을 제공 | 현재 Retention 설정 |
| 미발송 조건 | `no_new_coupon`으로 실제 미발송군만 학습하는 별도 실행을 지원. 적용 범위는 같은 적격성·개입 조건 | 현재 Retention 구현 |
| 초기 임계값 | 검증셋 F1을 최대화하는 값. 적용 시 정밀도·재현율·대상 인원을 함께 보고 | 현재 구현·임계값 분석 요구 |
| 확률 보정 | 기본 `calibration: auto`. 선택용 20%를 보정용 10%·최종 선택용 10%로 분리하고, 후자의 Log Loss·Brier가 모두 개선될 때 적용 | 개발 검증 기반 구현 기본값 |
| 모델 비교군 | 상수 확률, 방문 최근성 로지스틱, LightGBM·CatBoost·XGBoost, LSTM·GRU, ML+DL 앙상블 | 기존 구현·사용자 합의 |
| 독립 통합 평가 | 다른 seed로 생성한 새 데이터에 고정된 세 모델을 적용. 각 파트는 기존 내부 분할을 사용 | 이번 대화에서 정한 평가 방향 |
| 모니터링 | 반복 생성한 평가 실행에서 피처 분포와 성능을 비교하고 결과·알림을 저장 | 요구사항·이번 평가 방향 |

기본 정책 점수와 미발송 조건 점수는 `policy_condition`으로 식별한다. Retention의 확률은 방문 이탈이며, Uplift의 미발송 구매확률과는 결과 사건이 다르다.

추가 사용자 결정 없이 위 기준으로 구현을 진행할 수 있다. 튜닝 범위, 추가 피처 채택, 확률 보정 여부, 최종 모델은 개발 검증으로 선택하고 실행 기록에 남긴다.

## 3. 입력과 파트 간 연결

### 3.1 Retention 입력

학습은 같은 시뮬레이터 실행의 공식 피처 디렉터리와 `raw.sqlite`·`raw.manifest.json`을 사용한다. 공식 API `load_retention_inputs()`에서 snapshot·KIT39·성숙한 라벨을 읽고, 원장에서 과거 시퀀스와 추가 피처를 계산한다.

raw schema 5에서는 전체 SQLite 체크섬을 검증한 뒤 학습에 필요한 행·열을 조회한다. 추론은 공식 피처 생성에 필요한 전체 과거 이력을 조회한다. 전체 공식 로더와의 피처·시퀀스 일치 테스트를 함께 유지한다.

다음 검증을 유지하고 경계 사례를 보강한다.

- 데이터셋 ID, 원장 체크섬, 피처 버전, 통화·금액 단위, 고객·snapshot·기준시각의 일치.
- 원장의 미래 28일 세션으로 계산한 라벨과 제공 라벨의 일치.
- 실제 쿠폰 발송과 관측 정책의 일치.
- 기준일 이전 가입·최근 방문 적격성, 전체 결과 기간의 관측 여부.
- 미관측과 무활동의 구분, 계산 불가능한 평균·간격·비율의 결측 처리.
- 미래 정답 파일 없이 같은 피처·점수를 생성하는 추론 경로.

현재 연동은 설치된 시뮬레이터의 피처 버전과 일치하는 산출물을 요구한다. 이전 버전 자료는 현재 버전으로 다시 생성해 사용한다.

### 3.2 Uplift·CLV·전략

| 파트 | 현재 입력과 결과 | 연결 기준 |
| --- | --- | --- |
| Retention | 과거 행동으로 미래 28일 미방문 확률 | 타깃·기간·정책 조건을 출력에 기록 |
| Uplift | 과거 12주 주간 기록과 기준일 장바구니로 미래 4주 구매확률의 발송 효과 추정. T/X/H가 자체 결과 모델을 학습 | `p0`는 미발송 구매확률, `p1`은 발송 구매확률, 점수는 `p1-p0` |
| CLV | 과거 13주로 미래 52주 할인 후 실결제금액 예측. 자체 17개 피처와 공개 API 사용 | `predicted_clv_12m`의 실제 기간은 52주. 금액 단위와 정책 노출을 보존 |
| 전략 | 각 파트의 예측을 받아 우선순위·예산·대상 고객 결정 | 같은 데이터셋·고객·실제 기준시각으로 결합 |

연결 키는 `dataset_id`, `customer_id`, 시간대가 있는 기준시각을 기본으로 한다. `as_of_at`, `w0`, CLV의 예측 기준 `reference_week`를 UTC로 정규화해 같은 순간인지 확인한다. 시뮬레이터 주간 행의 `reference_week`는 해당 주의 시작이므로 CLV 출력의 예측 기준시각과 의미를 구분한다.

Retention 점수는 각 파트의 현재 공개 API에 맞춰 제공한다. Uplift·CLV의 자체 학습 경로를 활용하고, Retention 결과를 추가 학습 입력으로 사용할 필요가 생기면 그때 학습 외 예측 계약을 추가한다. CLV README에 남아 있는 쿠폰 효과와 Uplift의 중복 계상 검토는 전략 통합 평가에서 확인한다.

## 4. 피처와 모델 구현 기준

### 4.1 피처

공식 KIT39에 현재 추가한 10개 피처를 합쳐 49개 후보를 계산한다. `extra_features: false`로 KIT39만 사용하는 비교를 지원한다.

- 구매 주기 이상 1개, 과거 주문 수에 따른 여정 단계·체류 기간 2개.
- 동일 시각 행동 그룹의 전환 수·마지막 반복 길이 2개.
- 주문 수·실결제금액·평균 주문금액·고유 구매 상품 수·구매 수량의 상대 변화율 5개.

여정 단계는 과거 주문 수의 0·1·2·3회 이상 구분이다. 충성도를 설명하는 업무적 대리 지표로 문서화하고, 단계별 실제 관측 결과를 함께 확인한다.

피처 사전에는 계산식, 시간 창, 단위, 분모 0 처리, 필요한 관측 길이와 비즈니스 의미를 적는다. 요구사항의 30개 이상 정의, 변화율 5개 이상, 세션 품질 3개 이상, 시퀀스 피처 2개 이상과 각 컬럼을 대응시킨다. 시퀀스 임베딩과 행동 군집은 요구사항의 예시이므로 명시적인 순서 요약 2종을 초기 구현으로 사용한다.

변화율은 이전 값이 양수일 때 계산한다. 무구매·관측 부족·간격 표본 부족을 결측 사유로 구분한다. 결측 대체와 지시자는 학습 분할에서 적합한다. 극단값은 분포와 영향을 점검하고, 필요한 클리핑 경계도 학습 분할에서 산출한다. 실제 범위 밖의 가격·수량 등 계약 위반과 유효한 큰 주문을 구분한다.

실험 전 쿠폰 이력이 없는 시나리오에서는 쿠폰 피처가 상수·전체 결측일 수 있다. 후보 수, 실제 사용 수, 결측률과 상수 여부를 기록하고, 피처 기여는 같은 개발 분할의 제거 실험으로 판단한다.

### 4.2 모델과 선택

- ML은 검증된 라이브러리의 세 트리 모델을 사용한다. 클래스 가중치는 각 학습 표본에서 계산한다.
- DL은 PyTorch LSTM·GRU를 같은 고객·라벨·분할로 비교한다. 행동 네 종류의 개수와 과거 시간·세션 정보를 사용하고, 동일 timestamp의 미확인 순서는 그룹으로 처리한다.
- 현재 시퀀스 길이 128, Optuna 3회, 트리 120회, DL 최대 12 epoch는 초기 실행 설정이다. 표본 규모·학습 곡선과 개발 성능을 보고 조정한다.
- 튜닝은 개발 고객 안의 5-fold, DL Early Stopping은 개발 학습 고객 안의 별도 분할을 사용한다.
- 검증셋에서 ROC-AUC, 동률이면 Log Loss로 선택한다. ML+DL은 검증에서 고른 트리·시퀀스 모델의 고정 평균을 비교한다.
- 최근 방문일 기준선과 복잡한 모델의 추가 가치를 함께 보고한다. 학습·개발 검증에서 정한 선택을 최종 테스트에 적용한다.

## 5. 반복 시뮬레이션 평가 계획

### 5.1 실행 역할과 데이터 규모

| 실행 역할 | 데이터와 처리 | 사용 목적 |
| --- | --- | --- |
| 개발 | 생성 데이터 안에서 고객 60/20/20 분할. 60% 내부 5-fold 튜닝, 20% 모델·임계값 선택, 20% 모델별 홀드아웃 보고 | 모델 개발·개별 비교 |
| 독립 통합 평가 | 개발에 사용하지 않은 seed로 새 데이터 생성. 고정한 Retention·Uplift·CLV를 같은 새 실행에 적용 | 합쳐진 점수와 전략의 일반화 검증 |
| 모니터링 | 기준시점과 seed를 기록한 반복 실행에 같은 모델·전처리·임계값 적용 | 분포·성능 변화 기록과 알림 검증 |

모델 선택에 쓴 실행과 최종 통합 평가 실행을 구분한다. 독립 평가의 결과로 다시 튜닝하거나 전략을 선택했다면 다음 독립 실행을 최종 평가로 확보한다. 실행별 `dataset_id`와 모델 버전을 보존한다.

제출 데이터는 20,000명 이상, Treatment/Control 각각 10,000명 이상을 확인한다. 공통 기준일의 CLV 정답까지 확보하려면 24개월 생성을 기본 실행안으로 사용하고, 실제 미래 52주 완전 관측 여부를 확인한다. 500명·6개월 데이터는 빠른 연결 검증에 활용한다.

요구사항의 생성 이탈률은 15–25%다. 현재 기본 `source` 설정의 이탈률과 이 조건의 차이를 실행 리포트에 표시한다. 과제 조건의 검증은 기존 시뮬레이터가 지원하는 `target` 모드·목표 20%를 시작 설정으로 사용하고, 실제 28일 라벨의 전체·군별 이탈률을 측정한다. 설정 사본은 Retention 실행 범위에 두고, 시뮬레이터 설정 로더로 자산 경로를 해석한 뒤 적용한다. 생성 보정 방식과 원천 분포에서의 차이도 기록한다.

### 5.2 성능과 임계값

최종 리포트에는 ROC-AUC와 신뢰구간, PR-AUC와 실제 이탈률, Log Loss, Brier Score, 보정 곡선을 포함한다. 발송·미발송군, 관측 이력 길이별 표본 수와 클래스 수를 함께 기록한다.

과제의 ML AUC 0.78 달성 여부는 검증셋에서 선택한 트리 모델의 테스트 결과로 판정한다. 전체 우승 모델과 해당 트리 모델을 각각 표시한다. 단일 클래스·작은 하위집단에서는 지표의 계산 가능 여부와 표본 수를 보고한다.

초기 임계값은 검증 F1로 정하고, 적용 임계값에서 혼동행렬·정밀도·재현율·F1·대상 인원과 비율을 저장한다. 검증 예측을 생성한 60% 학습 모델을 최종 저장해 임계값과 확률 척도를 맞춘다. 확률·임계값·모델의 버전을 함께 기록한다.

확률 보정은 필요성을 개발 자료에서 확인한 뒤 추가한다. 보정기와 임계값 선택에 쓰는 점수는 해당 표본의 라벨을 학습하지 않은 모델에서 생성하고, 최종 테스트는 성능 보고에 사용한다.

### 5.3 모니터링

학습 기준 분포와 평가 실행의 분포를 PSI 또는 KS로 비교한다. 피처별 표본 수·결측률·분포 거리·판정 기준을 저장하고, 성숙한 28일 정답으로 시점별 AUC·Precision·Recall을 기록한다. 미성숙 결과는 관측 상태를 표시한다.

seed만 바꾸면 동일 생성 조건에서의 표본 변동을 확인할 수 있다. 시작일을 바꿔도 생성 분포가 같을 수 있으므로 시간 경과 자체를 drift로 해석하지 않는다. 변화 탐지·알림은 지원되는 생성 조건 또는 평가 표본 구성을 통제해 바꾼 시나리오로 검증한다. 정상 반복 실행의 변동과 표본 수를 고려해 알림 기준을 설정에 기록한다.

### 5.4 A/B 평가

실제 고객 배정과 이후 28일 방문 기록으로 군별 이탈률 차이를 계산한다. 전략 선택에 사용한 데이터와 독립된 실행에서 대상 선정·정책 효과를 검증한다. Power·p-value·신뢰구간을 포함한 전체 A/B 보고서는 전략·A/B 파트와 연결하고, Retention은 예측·모델 버전·결과 정의와 필요한 평가 지표를 제공한다.

## 6. 보완 작업과 완료 기준

아래 작업은 현재 구현을 보완하는 순서다. 새 구현 파일은 실제 기능을 담는 데 필요한 범위로 추가한다.

| 순서 | 작업 | 주요 대상 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | 입력 계약·시간 경계 검증 보강 | `simulator_input.py`, `tests/` | 공식 피처·원장 불일치, 기준시각 경계, 미래 기록 변경, 불완전 관측, 전원 제외 사례 확인 |
| 2 | 피처 사전·결측·이상치 처리와 제거 실험 | `simulator_input.py`, `models.py`, `pipeline.py` | 피처별 산식과 요구사항 대응, 학습 내 전처리, 기준선·KIT39·49개 후보의 개발 비교 |
| 3 | 최종 모델·임계값 일관성과 평가 리포트 | `pipeline.py`, `evaluate.py` | 실제 저장 모델에 대응하는 임계값·보정 상태·고정 임계값 지표, ML AUC 판정 분리 |
| 4 | SHAP·버전·실행 재현성 보완 | `evaluate.py`, `pipeline.py` | 설명 대상 모델·고객·시각·기준값·출력 척도 식별, 체크섬·설정·모델 버전 추적 |
| 5 | 독립 평가·모니터링 | `evaluate.py`, 필요한 모니터링 모듈 | 새 실행에서 고정 모델 평가, 군별 지표·PSI/KS·시점별 성능·알림 기록 |
| 6 | 공개 API·규모별 실행 점검 | `pipeline.py`, `__main__.py`, `readme.md` | import 가능한 배치 예측, 정답 없는 추론, 동일 키·상태 출력, 단계별 시간·메모리 측정 |
| 7 | 최종 제출 근거 정리 | `artifacts/`의 실행별 리포트 | 독립 평가 결과·모델 선택 근거·한계·필수 산출물 경로 대응 확인 |

SHAP은 어떤 모델을 설명하는지 명시한다. 최종 우승 모델이 최근 방문일·DL·앙상블일 때도 트리 SHAP이 생성될 수 있으므로, 트리 분석 결과와 실제 점수의 설명 대상을 명확하게 표시한다. 고객별 파일에는 고객·기준시각·설명 모델을 함께 저장한다.

추론은 선택된 모델과 그 구성 모델에 필요한 계산을 실행하도록 정리한다. 원천 로딩·공식 피처 생성·추가 피처·시퀀스·모델 추론의 시간과 메모리를 나눠 측정하고 제출 규모에서 확인한다.

실행 실패 후 재시도할 때 완성 모델과 부분 산출물을 구분할 수 있도록 완료 상태를 기록한다. 모델 저장 뒤 리포트 생성이 실패한 경우의 복구 절차도 점검한다.
